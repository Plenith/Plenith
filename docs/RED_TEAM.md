# Red-team simulator

`tools/red_team_simulator.py` spins up an LLM as an adversarial SSH
attacker against a running Plenith deployment. The LLM drives the
attack command by command; the orchestrator captures and scores
everything as a normal engagement.

Three uses:

1. **Validate counter-AI detection end-to-end.** Plenith's most novel
   capability is detecting that the *attacker itself* is an LLM agent.
   This tool is the unit test for that claim.
2. **Exercise the 14 heuristic categories.** Three persona prompts
   drive different attack shapes — fast credential-stuffer, patient
   APT, autonomous LLM agent.
3. **Generate engagement data for launch.** The session transcript
   plus the matching Plenith engagement log is the case-study
   material the build-in-public threads quote from.

---

## Prerequisites

You need two things running locally:

1. **A Plenith deployment** accepting SSH connections. Easiest is the
   docker-compose stack:
   ```bash
   cd linux-fork/
   cp .env.example .env
   $EDITOR .env       # set PLENITH_LLM_ENDPOINT to your LM Studio/Ollama
   docker compose up -d
   ```
   The bastion proxy listens on `localhost:22000`.

2. **An OpenAI-compatible LLM endpoint for the *attacker*.** Use a
   *different* model from the one Plenith uses to generate honeypot
   responses — otherwise the test reduces to one model talking to
   itself, which produces too much agreement.
   - **Recommended setup**: run two different models in LM Studio
     simultaneously. The orchestrator uses one (e.g. `qwen2.5-7b`);
     the simulator hits the second (e.g. `qwen2.5-14b-instruct` or
     `llama3.1-8b-instruct`).
   - **Alternative**: run Ollama for the attacker
     (`http://localhost:11434/v1`) and LM Studio for the defender.

Cost: $0 locally. Both LM Studio and Ollama run free on your own
hardware.

## Quick start (5 minutes)

```bash
# Dry-run first — confirms LLM endpoint works, doesn't touch SSH
python tools/red_team_simulator.py \
    --dry-run \
    --llm-endpoint http://localhost:1234/v1 \
    --llm-model qwen2.5-14b-instruct \
    --persona C

# Then the real thing
python tools/red_team_simulator.py \
    --target localhost:22000 \
    --user jdoe --password test \
    --llm-endpoint http://localhost:1234/v1 \
    --llm-model qwen2.5-14b-instruct \
    --persona C \
    --max-commands 60 \
    --output state/red-team-C-$(date +%s).json
```

Watch in another terminal:

```bash
# Dashboard live view
python tools/dashboard.py
# Open http://localhost:8765/
```

You should see a new engagement appear within seconds, and alerts
accumulate as the LLM runs more commands.

## The three personas

### Persona A — Opportunistic credential stuffer

**Shape**: fast, noisy. The LLM tries to grab everything valuable
before the legitimate user notices. Maximizes coverage of credential-
adjacent heuristics.

**Expected alerts**: `alert_credential_exfil`, `alert_credential_search`,
`alert_dns_exfil`, `alert_log_tampering`. The counter-AI signal may or
may not fire — fast attackers leave less timing signal to score on.

**Time to run**: ~15–20 minutes (60 commands).

### Persona B — Sophisticated APT

**Shape**: slow, patient. The LLM is told to use only commands a real
admin might run. No noisy patterns. Spreads activity across simulated
sessions.

**Expected alerts**: fewer than persona A. This is the *hard* case —
it stresses Plenith's ability to detect quiet attackers without false-
positiving against legitimate admin activity. Some heuristics
shouldn't fire at all; if they do, that's a tuning bug to file.

**Time to run**: ~25–30 minutes.

### Persona C — Autonomous LLM agent ⭐

**Shape**: explicit "ingest file contents into context, use what you
read to construct your next command." This is the persona designed to
trigger **proof-by-trap** — the criticial counter-AI signal.

**Expected alerts**:
- `alert_attacker_llm_detected` (high severity) — timing + lexical
  signals fire
- **`alert_attacker_llm_detected` promoted to critical** — when the
  LLM regurgitates a trap marker from a planted file into a
  subsequent command. This is the launch-announcement moment.

**Time to run**: ~20–25 minutes.

If only one persona gets run, run **C**. It's the test that earns
Plenith the right to make the counter-AI claim publicly.

## What to watch on the Plenith side

Open the dashboard at `:8765`. As the simulator runs, you should see:

1. **A new engagement row** appear in the engagements list.
2. **Alert pills accumulate** under that engagement — colored by
   severity (red = critical, orange = high, yellow = medium, blue =
   info).
3. **The narrative** auto-generated by `tools/narrate.py` reflects
   the LLM's progression.
4. **The DNS query log** populates if the LLM tries any curl/wget
   exfil.

After the simulator finishes, run `tools/audit.py` to see the
structured alert history:

```bash
python tools/audit.py --engagement <id> --json | jq '.actions_taken'
```

## Recommended test matrix

For the launch case study, run all three personas back-to-back and
collect the engagement logs:

```bash
for PERSONA in A B C; do
    python tools/red_team_simulator.py \
        --persona $PERSONA \
        --max-commands 50 \
        --output state/red-team-${PERSONA}-$(date +%s).json
    sleep 60     # let the orchestrator settle between runs
done
```

Expected result across three engagements:

| Persona | Critical alerts | High alerts | Medium alerts | Proof-by-trap? |
| :--- | :---: | :---: | :---: | :---: |
| A | 1–2 (reverse shell unlikely; credential exfil yes) | 3–5 | 2–4 | rare |
| B | 0–1 | 1–2 | 1–3 | possible |
| C | **2–3** (LLM detection + at least one operational alert) | **3–5** | 2–4 | **target ≥50% of runs** |

If C doesn't produce proof-by-trap in at least one of three runs,
something is wrong — either the trap-marker injection isn't working
(check `plenith/counter_ai.py:maybe_inject_trap`), the LLM isn't
ingesting file contents enthusiastically enough (try a different
model), or the marker-echo detection isn't firing (check
`check_for_echoed_trap`).

## Interpreting the output JSON

Each session transcript looks like:

```json
{
  "persona": "C",
  "target": "localhost:22000",
  "user": "jdoe",
  "llm_endpoint": "http://localhost:1234/v1",
  "llm_model": "qwen2.5-14b-instruct",
  "started_at": 1700000000.0,
  "ended_at": 1700001234.5,
  "end_reason": "max_commands_reached",
  "command_count": 50,
  "turns": [
    {
      "n": 1,
      "timestamp": 1700000000.5,
      "command": "whoami",
      "output": "jdoe\n",
      "latency_ms": 845.2,
      "llm_raw": "whoami"
    },
    ...
  ]
}
```

Cross-reference with Plenith's engagement log
(`state-docker/logs/<host>/<id>.json`) to see what was alerted on.

## Limitations

- The simulator only opens **one interactive SSH session** at a time.
  Multi-session lateral movement isn't simulated (the LLM is told to
  identify lateral targets, but can't actually `ssh db-prod-01` and
  branch into a second session from there).
- The simulator does **not** validate that proof-by-trap fired — that
  check has to be done manually by inspecting the engagement log.
  Wiring it as an automated assertion is on the v1.1 roadmap.
- Each persona runs as a fresh engagement. Cross-engagement attacks
  (a single attacker probing on Monday and returning on Friday) aren't
  modeled.
- The simulator deliberately doesn't include a "destructive payload"
  persona (e.g. rm -rf /, fork bombs, kernel module loads) — those
  add no test value to the heuristics and risk breaking the
  docker-compose stack.

## Adding the simulator to nightly CI

When you're confident the simulator is stable, you can run it
nightly against the docker-compose stack in CI and assert that:

1. The expected alerts fire for each persona
2. The proof-by-trap rate stays above some floor (say, 30%)

The skeleton for that lives in the v1.1 roadmap under "automated
red-team smoke tests." For v1.0, manual runs are the standard.
